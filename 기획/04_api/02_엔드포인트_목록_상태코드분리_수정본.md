# 02. 엔드포인트 목록 (도메인별) — 회의 반영 수정본

> 이 문서가 **8명 사이의 컨트랙트**입니다. 여기 없는 엔드포인트는 만들지 않습니다. 추가가 필요하면 PM에게 제안 → 문서 먼저 갱신 → 구현 순서로 진행합니다.

> 표 보는 법: 🔓=로그인/회원가입 진입 전 허용, ✅=USER 이상 인증 필요, 🛡=ADMIN 이상, 👑=SUPER_ADMIN/root 전용

## 0. 2026-05-22 회의 반영 핵심 결정

### 인증 / 회원가입

- 로그인 방식은 **Form + OAuth2(Google, Naver)** 를 병행한다.
- 구현 우선순위는 **Form → Google → Naver** 순서로 둔다.
- Kakao는 이메일 매칭이 복잡해질 수 있으므로 v1에서는 예외 케이스로 보고 **Form 회원가입을 권장**한다.
- 가입 가능 여부는 **이메일 화이트리스트**로 제한한다.
- Form 회원가입 시 `realName`, `nickname`, `major`를 받는다.
- `major == null`인 사용자는 로그인 후 **내 정보 보완 페이지로 리다이렉트**하고, 보완 전까지 다른 페이지 이동을 제한한다.
- 가입 이후 일반 유저는 `realName`, `major`를 직접 수정할 수 없다. 수정은 관리자 정책 영역으로 둔다.
- Redis, 분산락은 v1 이후로 보류한다.

### 권한 / 운영

- 일반 에셋 게시글은 저작권 및 내부 공유 정책 때문에 **비회원 열람 불가**로 변경한다.
- 권한 변경 같은 운영 작업은 **SUPER_ADMIN/root 전용**으로 둔다.
- **분쟁 처리·글 강제 삭제·메시지 강제 열람 등 강한 운영 권한은 본 프로젝트 범위 밖**으로 본다. Admin은 **모니터링과 통계 조회 중심**으로만 둔다.
- 요청 게시판 흐름은 **요청자와 Assignee(TA) 중심**으로 설계한다. **어드민 개입 없음.**

### 파일 정책

- 파일 도메인은 에셋 파일뿐 아니라 **게시글 썸네일, 프로필 이미지, 요청 게시판 참고 썸네일**까지 공통으로 관리한다.
- 파일 업로드 요청은 각 도메인 API에서 multipart로 받고, 실제 저장/검증/메타데이터 관리는 File 도메인 서비스에 위임한다.
- 파일 다운로드/이미지 조회도 로그인 사용자에게만 허용한다.
- 다운로드 로그/파일 통계는 MVP 범위에서 제외하고, 추후 Analytics/Audit 또는 운영 모니터링 범위에서 재검토한다.

### 요청 게시판 상태 흐름 (어드민 개입 없음, GitHub Issue 닫히듯 자동 완료)

상태는 5개로 통일한다.

```text
REQUESTED(요청됨) → IN_REVIEW(검토중) → IN_PROGRESS(제작중) → COMPLETED(완료)
                                      ↘ REJECTED(반려됨)
```

흐름:

1. **요청 작성** — Unity/Unreal 반(요청자)이 `POST /api/requests`. `status=REQUESTED`.
2. **수락 (assign = TA가 본인을 assignee로 등록)** — TA(USER 권한 누구나)가 `PATCH /api/requests/{id}/assign`. assigneeId 가 본인. `status` 자동으로 `IN_PROGRESS`. (IN_REVIEW 는 선택 단계로만 두고 본 MVP는 REQUESTED → IN_PROGRESS 직행 권장)
3. **작업** — assignee 가 자유롭게 작업.
4. **완료 — 자동 전환** — assignee 가 에셋 게시글 작성할 때 `linkedRequestId` 필드에 요청 ID를 박는다. 게시글 저장과 동시에 해당 요청의 `linkedPostId` 설정되고 `status` 자동 `COMPLETED`. (별도 `link-post` 호출 없이 게시글 작성 한 번으로 끝.)
5. **반려** — assignee 또는 요청자가 `PATCH /api/requests/{id}/reject` 사유 작성. `status=REJECTED`.
6. **재오픈** — 요청자가 `PATCH /api/requests/{id}/reopen` 으로 `REQUESTED` 또는 `IN_REVIEW`로 되돌릴 수 있다.

원칙:

- 어드민 권한 (`🛡`) 은 본 흐름에 **개입하지 않는다**. 운영자는 조회·모니터링만.
- 요청이 `IN_PROGRESS`로 들어가면 요청자는 본문을 수정할 수 없다.
- 한 요청에는 Assignee 를 1명만 배정한다. 멀티 Assignee는 v1 범위에서 제외한다.
- 모든 상태 변경 시 요청자에게 시스템 DM 자동 발송.
- 수락/반려 등 액션은 프론트에서 확인 팝업을 띄운다.

### 게시글에 요청 연결 (linkedRequestId)

- `POST /api/posts` 요청 본문(`data`)에 선택 필드 `linkedRequestId` 추가.
- 값이 있으면 서비스가 해당 요청의 assignee == 현재 사용자 인지 검증하고, 요청 status 를 `COMPLETED` 로 자동 전환 + `linkedPostId` 설정.
- 값이 없으면 일반 에셋 게시글로 동작.

## 1. 공통 응답 규칙

일반 JSON API는 모두 `ApiResponse` 래퍼를 사용한다.

```json
{
  "success": true,
  "data": {}
}
```

```json
{
  "success": false,
  "error": {
    "code": "ERROR_CODE",
    "message": "사용자에게 보여줄 수 있는 메시지"
  }
}
```

단, 파일 다운로드처럼 실제 바이너리를 반환하는 API는 `ApiResponse`로 감싸지 않는다.

모든 엔드포인트 표는 아래 컬럼 형식을 따른다.

```md
| Method | Path | 기능 | Auth | 요청 | 응답 | 상태 코드 | 비고 |
```

## 4. Request 게시판 · `/api/requests/**`

| Method | Path | 기능 | Auth | 요청 | 응답 | 상태 코드 | 비고 |
|---|---|---|---|---|---|---|---|
| POST | `/api/requests` | 에셋 요청 작성 | ✅ | multipart `data`, `referenceThumbnail?` | `ApiResponse<RequestResponse>` | 201 | status=`REQUESTED`. 참고 썸네일 선택 |
| GET | `/api/requests` | 요청 목록 | ✅ | `?page&size&status&assigneeId&requesterId&teamId&q` | `ApiResponse<Page<RequestSummaryResponse>>` | 200 | 내부 회원만 |
| GET | `/api/requests/{id}` | 요청 상세 | ✅ | - | `ApiResponse<RequestResponse>` | 200 | linkedPostId 포함 |
| PUT | `/api/requests/{id}` | 요청 수정 | ✅(요청자) | multipart `data`, `referenceThumbnail?` | `ApiResponse<RequestResponse>` | 200 | `REQUESTED` 상태에서만 수정 |
| PATCH | `/api/requests/{id}/assign` | TA가 본인을 assignee로 수락 | ✅(USER) | - (본문 없음, 호출자 자동 assignee) | `ApiResponse<RequestResponse>` | 200 | 1명만 배정. 자동 `IN_PROGRESS`. 이미 assignee 있으면 409 |
| PATCH | `/api/requests/{id}/reject` | 요청 반려 | ✅(assignee 또는 요청자) | `{reason}` | `ApiResponse<RequestResponse>` | 200 | DM 발송. 확인 팝업 필요 |
| PATCH | `/api/requests/{id}/reopen` | 반려 요청 재오픈 | ✅(요청자) | `{targetStatus}` | `ApiResponse<RequestResponse>` | 200 | `REQUESTED` 로 복귀 |
| DELETE | `/api/requests/{id}` | 요청 삭제 | ✅(요청자) | - | `ApiResponse<Void>` | 200 | `REQUESTED` 상태만 soft delete |

> **자동 완료 흐름**: 별도 `/link-post` 엔드포인트는 두지 않는다. assignee 가 에셋 게시글 작성 시(`POST /api/posts`) 본문에 `linkedRequestId` 를 넣으면 서비스가 요청 상태를 자동 `COMPLETED` 로 전환하고 `linkedPostId` 를 세팅한다. (GitHub Issue 가 PR 머지로 자동 닫히는 것과 동일한 패턴)
>
> **어드민 개입 없음**: 본 흐름에는 `🛡` 권한 작업이 없다. 운영자는 `GET /api/requests` 로 모니터링만 가능.
>
> **`/review` 단계는 본 MVP에서 사용하지 않음**: TA 가 본인을 직접 수락(`/assign`)하는 흐름이라 별도 검토 단계 불필요. 상태 enum 에는 남겨두되 v1.1에 도입 검토.

> 다운로드 로그 및 파일 통계 API는 MVP 범위에서 제외한다. 필요하면 추후 `analytics` 또는 `audit` 도메인으로 분리한다.

## 8. Tag / Search

- 태그 생성·연결은 Post 작성/수정 시 내부적으로 `TagService.findOrCreate(name)`에서 처리한다.
- 인기 태그는 `GET /api/posts/popular-tags`를 사용한다.
- 기본 검색은 `GET /api/posts`의 `q`, `tag`, `categoryId`, `authorId`, `teamId` 쿼리 파라미터로 처리한다.

## 9. Message(DM) · `/api/messages/**`, `/api/admin/messages/**`

| Method | Path | 기능 | Auth | 요청 | 응답 | 상태 코드 | 비고 |
|---|---|---|---|---|---|---|---|
| GET | `/api/messages/inbox` | 대화방 목록 | ✅ | `?page&size` | `ApiResponse<Page<MessageThreadResponse>>` | 200 | 상대별 최신 메시지 |
| GET | `/api/messages/conversation/{partnerId}` | 1:1 대화 조회 | ✅ | `?page&size` | `ApiResponse<Page<MessageResponse>>` | 200 | DESC 정렬 |
| POST | `/api/messages` | DM 보내기 | ✅ | `MessageSendRequest{toUserId,content}` | `ApiResponse<MessageResponse>` | 201 | 송신 후 WS 푸시 |

### WebSocket(STOMP)

| 구독 토픽 | 목적 |
|---|---|
| `/user/queue/messages` | 본인 수신함 푸시 |
| `/user/queue/messages.unread` | 안 읽은 수 변경 푸시 |

> 클라이언트는 메시지 송신을 `POST /api/messages`로 통일한다. WebSocket은 서버 푸시 전용으로 사용한다.
